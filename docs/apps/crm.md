# apps.crm

## Objetivo

`apps.crm` é o funil de vendas/CRM do LocusHub: gerencia `Opportunity` desde a criação até o fechamento (ganho ou perdido), organizadas num Kanban por `OpportunityStage` configurável. Reutiliza `apps.clients.models.Client` como fonte oficial de cliente (nunca cópia, nunca escreve). Inclui registro de atividades comerciais (`CommercialActivity`), histórico estruturado de mudança de etapa (`OpportunityStageChange`) e configuração de Origem/Etapa/Motivo de perda.

Desde 14/09/2026 (implementação "Produtos e Serviços"), também inclui a composição comercial completa de uma negociação: `Proposal`/`ProposalVersion`/`ProposalItem`/`Contract` — versionamento, snapshots, cálculo financeiro, emissão de PDF (Proposta Comercial/Contrato) e aceite (que fecha a `Opportunity` via `change_opportunity_stage()`, nunca um caminho paralelo). Agenda central, dashboard, financeiro, comissão, automações, integrações externas e **tabela de preços** (`PriceTable`) ficam para etapas futuras — ver seção "Preparação para PriceTable" no relatório final.

Desde a RODADA 3 DE REFINAMENTOS DO HUB DA OPORTUNIDADE (14/09/2026, mesma data — sessão seguinte), também inclui: observações rápidas na Visão Geral, `ActivityType` configurável (deixou de ser `TextChoices`), nomenclatura de exibição "PROPOSTA-000123" para propostas, desconto de item em R$ (não mais percentual), reorganização do bloco "Documento" com download automático do PDF gerado, a ação "Retomar negociação" (reabre uma Oportunidade ganha) e o vínculo real Oportunidade↔patrimônio (`OpportunityEquipment`, aba Equipamentos) — ver seção "RODADA 3" abaixo para o resumo completo e as seções de cada model/service/view para o detalhe.

Desde a RODADA 4 DE REFINAMENTOS DA COMPOSIÇÃO COMERCIAL (15/09/2026), a tela "Produtos e Serviços" ganhou: **auto-versionamento preguiçoso** (a primeira edição real depois de uma emissão clona uma nova versão DRAFT nos bastidores — o usuário nunca mais precisa clicar em "Criar nova versão", botão que foi removido; a versão emitida permanece imutável), **itens de Serviço** além de Equipamento (`ProposalItemType`, novo catálogo mínimo `ServiceCatalogItem`, semeado só com "Hora técnica"), remoção de item por um modal de confirmação próprio (nunca o `confirm()` nativo do navegador), e a remoção do bloco "Aceite" desta tela — o único CTA de aceite comercial visível no Hub continua sendo "Orçamento aceito", no topo da página. Ver seção "RODADA 4" abaixo para o resumo completo.

## Models

Arquivo: `apps/crm/models.py`.

Gerenciado em `configuracoes/tipos-atividade/` (list/create/update — **nunca delete**, mesmo padrão de todo o resto do catálogo de configuração). **`CommercialActivity`** — `opportunity` (CASCADE), `activity_type` (agora FK para `ActivityType`, migrado de `CharField` livre via migration de dados — `0005_convert_activity_type_to_fk.py`), `description`, `occurred_at`, `scheduled_for` (alimentará futura Agenda Central), `completed_at`, `created_by` (PROTECT). Sem histórico (sem fluxo de edição/exclusão). `Meta.permissions`: `view_commercial_activities`, `add_commercial_activities`.

"hora"; vazio para itens de equipamento), `quantity` (`PositiveIntegerField`), `unit_price`, **`item_discount_amount`** (`Decimal`, R$ — RODADA 3, 14/09/2026: convertido de percentual (`item_discount_percent`, 0–100) para VALOR MONETÁRIO via migration de dados `0006_item_discount_percent_to_amount.py`, preservando o desconto efetivo já gravado, `AddField` nullable → `RunPython` backfill → `RemoveConstraint` → `RemoveField`/`AlterField` numa única migration), `line_total` (calculado, nunca editado direto — cálculo idêntico para equipamento e serviço, ver `calculate_proposal_version()`), `notes`, `order`. `CheckConstraint`s: quantity > 0, unit_price ≥ 0, `0 ≤ item_discount_amount ≤ quantity × unit_price` (via `F()` expressions — nunca maior que o valor bruto do item), line_total ≥ 0, mais a `proposal_item_type_matches_single_reference` acima. Único caminho de escrita de `stage`/`won_at`/`lost_at`/`loss_reason`/`closed_value`. Regras: rejeita mesma etapa/etapa inativa; ganho → seta `won_at`, limpa perda; perda → exige `loss_reason`; etapa intermediária → reabre, limpa todo estado de fechamento. Sempre cria `OpportunityStageChange`.
- `create_activity(data)` — valida `activity_type`.
- `preview_opportunity_hard_delete()` / `hard_delete_opportunity(*, opportunity_id, actor)` — `select_for_update()`, exige `actor.is_superuser`, cascade automático de stage_changes/activities. Desde 14/09/2026 a prévia também soma "propostas (com versões e itens)" e, desde a RODADA 3, "vínculos de equipamento" como dependentes; se alguma versão já tiver `Contract` (PROTECT), o hard delete é bloqueado pela mesma engrenagem `HardDeleteBlocked`/`describe_protected_error` já usada para outros FKs protegidos — nenhuma lógica nova de bloqueio foi criada. `OpportunityEquipment.opportunity` é `CASCADE` (o ponteiro em si some junto), mas `equipment`/`linked_movement`/`unlinked_movement` são `PROTECT` apontando PARA FORA — excluir a Oportunidade nunca cascateia para o `Equipment`/`Movement` reais, que continuam intactos.
- **`OBSERVATION_ACTIVITY_TYPE_CODE = "OBSERVACAO"`** + `get_observation_activity_type()` (RODADA 3) — resolve o `ActivityType` usado pelo botão "+" de Observações da Visão Geral; é o ÚNICO código de `ActivityType` referenciado por código em todo o projeto (todos os demais tipos são configuração livre do Administrador).

### Produtos e Serviços / Proposta Comercial (14/09/2026)

- `_require_draft(version)` — helper interno; toda função que edita uma `ProposalVersion` chama isso primeiro e levanta `ValueError` se `status != DRAFT` (é o mecanismo real de imutabilidade pós-emissão, não só uma checagem de UI).
- `_next_document_number(*, key, prefix)` — `@transaction.atomic`, `get_or_create` + `select_for_update()` + incremento de `NumberingCounter`, retorna `f"{prefix}-{last_value:06d}"`. Mesmo padrão de `EquipmentModel.last_sequence`.
- **`calculate_proposal_version(version)`** — fonte única de verdade do financeiro (spec seção 24): para cada item, `gross = unit_price * quantity`, subtrai **`item_discount_amount`** (RODADA 3: valor monetário direto, `line_total = gross - item_discount_amount` — antes era um percentual aplicado sobre `gross`), soma tudo em `subtotal`; `total = subtotal - general_discount + interest_amount + freight_amount`. Levanta `ValueError` se o total resultante for negativo — **nunca** arredonda/trava silenciosamente para zero. Sempre `Decimal`. Chamada por toda operação que muda item ou condições, nunca calculada na view/template.
- `create_proposal(*, opportunity, created_by)` / `get_or_create_active_proposal(*, opportunity, created_by)` — cria `Proposal` (numerada) + 1ª `ProposalVersion` (DRAFT); a segunda é o acessor canônico usado tanto pela tela (`OpportunityDetailView.get()`) quanto pelos endpoints POST de item (`_get_editable_version_or_404`), garantindo que adicionar o primeiro item nunca depende de uma visita prévia à página.
- **`ProposalItemData`** + `_validate_item_fields()` — quantity > 0, unit_price ≥ 0, desconto 0–100. Desde a RODADA 4 (15/09/2026) também valida `item_type`: exatamente uma referência (`equipment_model` XOR `service`) preenchida e coerente com o tipo — mesma regra da `CheckConstraint` do model, checada aqui antes para devolver uma mensagem amigável em vez de um `IntegrityError` cru. `_describe_item()` (RODADA 4) resolve `(description_snapshot, unit_label_snapshot)` a partir da referência: `service.name`/`service.unit_label` para item de Serviço, `f"{equipment_model.name} ({equipment_model.code})"`/`""` para Equipamento.
- `add_proposal_item()` / `update_proposal_item()` / `remove_proposal_item()` — todas chamam `_require_draft()` primeiro, depois `calculate_proposal_version()`.
- **Auto-versionamento preguiçoso (lazy) — `ensure_editable_version()`/`ensure_editable_item()`** (RODADA 4, 15/09/2026, seção 9-13): a solução para o usuário não precisar clicar manualmente em "Criar nova versão" para continuar editando depois de uma emissão, SEM abrir mão da imutabilidade de uma versão emitida (seção 10, regra crítica). `ensure_editable_version(*, proposal, created_by)` devolve a `latest_version` já em DRAFT sem nenhuma escrita nova (idempotente — chamar de novo antes de outra alteração real reaproveita o MESMO rascunho, evitando versões vazias) ou, se a mais recente já foi emitida/aceita, clona uma nova versão DRAFT na hora via `create_new_version()` (reaproveitado 100%, nenhuma lógica de clonagem nova). `ensure_editable_item(*, item, created_by)` faz o mesmo para um item específico exibido na tela (que pode pertencer a uma versão que acabou de deixar de ser DRAFT) — localiza, na nova versão clonada, a linha correspondente pelo mesmo `order` (estável através da clonagem). **"Lazy" é a palavra-chave**: essas funções só são chamadas pelos endpoints POST de mutação (adicionar/remover/editar item, salvar condições) — nunca por um GET/carregamento de página, então abrir ou recarregar a tela NUNCA cria uma versão nova por si só; só a PRIMEIRA alteração de verdade decide clonar, e a versão emitida original nunca é tocada.
- `ProposalConditionsData` + `update_draft_conditions()` — grava condições comerciais/logística/financeiro/texto livre de uma vez; valida `general_discount`/`interest_amount`/`freight_amount` ≥ 0; recalcula ao final. **CORREÇÃO (15/09/2026)**: também valida que `data.delivery_location`, quando informado, pertence ao MESMO cliente da `Opportunity` da própria `proposal_version` (`delivery_location.client_id == proposal_version.proposal.opportunity.client_id`) — levanta `ValueError` caso contrário. É a SEGUNDA camada de defesa (a primeira é a queryset de `ProposalConditionsForm`, escopada pelo `opportunity` da URL — ver Forms/Views abaixo); protege o service mesmo que seja chamado de outro lugar no futuro sem passar por aquele form.
- `AvailabilityResult` (`requested`, `available`, propriedade `missing`) + `check_availability(*, equipment_model, requested_quantity)` — **somente leitura**: conta `Equipment` ativo com `status=DISPONIVEL` do modelo pedido, reaproveitando o campo operacional real (`apps.equipment.models.Equipment.status`) já usado pelo resto do sistema. Nunca cria reserva/movimento, nunca seleciona patrimônio específico (spec seção ~40-45).
- `_format_address_snapshot()` / `_format_company_address_snapshot()` — formatadores internos usados só por `issue_proposal()`.
- **`issue_proposal(*, proposal_version, issued_by)`** — `@transaction.atomic`; exige DRAFT e ≥1 item; recalcula; congela snapshot de cliente (de `opportunity.client`), empresa (de `get_company_profile()`) e vendedor (`str(opportunity.owner)`); muda status para ISSUED; gera o PDF (`apps.crm.pdf.render_proposal_pdf`) e cria o `Attachment` (categoria `ORCAMENTO_PROPOSTA`, origem `SYSTEM`). A partir daqui a versão vira imutável (`is_editable=False`).
- `create_new_version(*, proposal, created_by)` — exige que a última versão exista e **não** esteja DRAFT; clona condições + itens para uma nova `ProposalVersion` (`version_number + 1`, DRAFT); recalcula. É o único caminho para "editar" uma proposta já emitida — nunca uma edição silenciosa da versão antiga. Até a RODADA 3 só era acionado por um botão manual ("Criar nova versão"); desde a RODADA 4 (15/09/2026) esse botão foi removido e a função passou a ser chamada **automaticamente** por `ensure_editable_version()` (acima) na primeira mutação após uma emissão — a função em si não mudou nenhuma linha, só ganhou um novo chamador.
- `generate_contract(*, proposal_version, created_by)` — rejeita se a versão ainda for DRAFT; numera via `NumberingCounter` (prefixo `CONTR-`); cria `Contract`; gera PDF (`render_contract_pdf`) e `Attachment` (categoria `CONTRATO`).
- `DocumentType` (TextChoices): PROPOSTA, CONTRATO, PROPOSTA_E_CONTRATO — **sempre dois documentos distintos quando ambos são pedidos, nunca um PDF híbrido** (spec: "Proposta Comercial" e "Contrato" são documentos separados).
- `generate_documents(*, proposal_version, document_type, actor)` — `@transaction.atomic`; orquestra `issue_proposal()`/`generate_contract()` conforme `document_type` (emite automaticamente se ainda DRAFT e o contrato foi pedido diretamente); retorna um dict com as chaves geradas mais, desde a RODADA 3, `"download_attachment"` (o `Attachment` de Orçamento/Contrato recém-gerado — ou o já existente, se chamado duas vezes sobre a mesma versão já `ISSUED`, nunca duplicado) usado pelo download automático do PDF no redirect (`?baixar_pdf=<pk>`, validado contra IDOR em `OpportunityDetailView.get()`).
- `acceptable_proposal_versions(opportunity)` — QuerySet de versões ISSUED (ainda não aceitas) de todas as `Proposal`s da oportunidade — é o universo válido usado para validar o POST de aceite (proteção IDOR).

## Permissions

**Por que só 2 permissions novas, e não uma por ação** (spec seção 83, "evitar excesso de permissions"): toda a composição da proposta (adicionar/editar/remover item, salvar condições, criar nova versão) reaproveita `crm.change_opportunities` — é conceitualmente "editar dados da oportunidade", a mesma permissão que já protegia a ficha. Aceitar reaproveita `crm.change_opportunity_stage` — aceitar É uma mudança de etapa (para uma etapa ganha), não uma ação nova. Só emitir Proposta (produz um documento comercial formal, número definitivo, snapshot congelado) e gerar Contrato (produto jurídico) ganharam permissão própria, porque são ações qualitativamente diferentes de "editar um rascunho" — o resto seria duplicação.

**RODADA 4 (15/09/2026) também não criou NENHUMA `Permission` nova** — o CRUD de `ServiceCatalogItem` reaproveita `crm.manage_commercial_settings` (mesma permissão de Origem/Etapa/Motivo de perda/Tipos de atividade); adicionar/editar/remover um item de Serviço reaproveita `crm.change_opportunities` (mesma permissão que já cobria item de Equipamento — "item comercial" continua sendo um único conceito de permissão, independente do tipo).

**RODADA 3 (14/09/2026) não criou NENHUMA `Permission` nova** — "Retomar negociação" reaproveita `crm.change_opportunity_stage` (é literalmente uma mudança de etapa); a gestão de `ActivityType` reaproveita `crm.manage_commercial_settings` (mesma permissão de Origem/Etapa/Motivo de perda); vincular/desvincular equipamento reaproveita **`operations.register_operations`** (a Permission já existente desde a Fase 1, mirror de `CAN_REGISTER_OPERATIONS`, do catálogo de `apps.accounts.permission_catalog`) — é a primeira vez que uma view de `apps.crm` checa uma Permission de OUTRO app_label (`("crm.view_opportunities", "operations.register_operations")`), o que só funciona porque a arquitetura de Cargo/`Permission` nativa do Django não é particionada por app: um mesmo Cargo pode combinar Permissions de `crm`+`operations` livremente, exatamente o que torna possível "CRM/comercial pode VER, Operação pode vincular/devolver" sem inventar uma permissão híbrida nova.

## Pontos importantes

- **Único app nascido 100% na arquitetura de Cargo** — as 9 permissions `crm.*` são as únicas do catálogo sem `legacy_constant`. CRM foi construído depois da aprovação da nova arquitetura, então nunca passou pelo sistema legado.
- **Botão escondido ≠ bloqueio no backend** — a autorização real é sempre `PermissionRequiredMixin`; POST manual de campos de perda/ganho (ou de qualquer ação de Produtos e Serviços) sem permissão é bloqueado mesmo que o botão nunca tivesse aparecido (testado explicitamente).
- **`get_object_or_404` sem filtro por usuário/dono é deliberado** — a proteção contra IDOR é a permissão (`view_opportunities`), não esconder o PK. Para o aceite de proposta especificamente, há uma segunda camada: o `proposal_version` submetido precisa estar em `acceptable_proposal_versions(opportunity)`.
- **Dupla camada de validação**: toda regra crítica (ganho/perda mutuamente exclusivos, valores não-negativos, total nunca negativo) tem `CheckConstraint` no banco E validação explícita em `clean()`/services.
- **`TrigramWordSimilarity` vs `TrigramSimilarity`**: escolha documentada por medição manual — `word_similarity` mede o melhor trecho contínuo do nome, mais adequado para buscas curtas contra nomes longos.
- **Aba "Equipamentos" deixou de ser estado vazio estático (RODADA 3, 14/09/2026)** — `OpportunityEquipment` é o vínculo real Oportunidade↔patrimônio, via `create_movement()`. Continua sem relação com a composição da proposta (`ProposalItem` é por `EquipmentModel`/quantidade, nunca por patrimônio individual — os dois conceitos são deliberadamente independentes: "o que foi orçado" ≠ "qual patrimônio físico foi de fato instalado"). Aba "Anexos" também deixou de ser omitida: `apps.attachments` tem implementação real (ver `docs/apps/attachments.md`).
- **"Criar/salvar" ≠ "emitir" ≠ "aceitar"** — três verbos, três funções de `services.py` distintas (`create_proposal`/`update_draft_conditions`, `issue_proposal`, `accept_proposal_version`), nunca fundidos numa única ação. Emitir não implica aceitar; gerar contrato não implica aceitar. Desde a RODADA 3, "vincular equipamento"/"desvincular" também nunca implicam ganho/perda — são puramente operacionais (`create_movement()`), nunca escrevem `stage`/`won_at`/`closed_value`.
- **`Proposal` não guarda `status` próprio** — sempre derivado de `latest_version.status` (`display_status`), para nunca ter duas fontes de verdade divergentes.
- **Limitação conhecida de UI**: `update_proposal_item()`/`ProposalItemUpdateView` existem e têm cobertura de teste, mas `_proposal_composition.html` só oferece botões de adicionar/remover item — não há um controle de "editar" inline na tela; para mudar quantidade/preço de um item já adicionado, hoje é preciso remover e adicionar de novo. Disclosed no relatório final.
- **RODADA 4 — versão emitida continua imutável, mesmo com auto-versionamento**: `ensure_editable_version()`/`ensure_editable_item()` NUNCA escrevem numa versão `ISSUED`/`ACCEPTED` — elas decidem clonar uma nova versão DRAFT (via `create_new_version()`) e é NESSA nova versão que a mutação pedida é de fato aplicada; a versão emitida original permanece bit-a-bit como estava, incluindo o PDF já gerado (nunca sobrescrito) e o `Attachment` já criado. "Lazy" é literal: nenhuma dessas funções é chamada por um GET — só pelos endpoints POST de mutação — então abrir/recarregar a página nunca cria uma versão nova por conta própria.
- **RODADA 4 — nenhuma migration destrutiva**: `0008_proposal_item_service_type.py` é 100% aditiva (`CreateModel(ServiceCatalogItem)` + `AddField`s + uma `CheckConstraint` nova) — nenhum `ProposalItem` já gravado precisou de backfill, porque `item_type` tem `default=EQUIPAMENTO` e os `ProposalItem`s existentes já tinham `equipment_model` preenchido/`service` vazio, batendo com a nova `CheckConstraint` sem nenhum ajuste manual de dado.
- **RODADA 4 — "converter" um item de Serviço em Equipamento (ou vice-versa) não é uma operação suportada** — `item_type` é decidido na criação do item (`add_proposal_item()`) e nunca migrado por uma função dedicada; para "trocar o tipo" de um item já adicionado, a UI atual exige remover e adicionar de novo (mesma limitação já documentada acima para editar quantidade/preço inline) — nenhum service de "converter" foi criado, por não fazer parte do escopo pedido nesta rodada.
- **RODADA 3 — reuso de Permission entre apps**: vincular/desvincular equipamento é a primeira ação de `apps.crm` a exigir uma `Permission` de OUTRO `app_label` (`operations.register_operations`) além de `crm.view_opportunities` — deliberado (ver seção Permissions), não um acoplamento acidental.
- **RODADA 3 — nenhuma migration destrutiva**: a conversão de `activity_type` (texto→FK) e de desconto (percentual→R$) seguiram sempre o padrão `AddField` nullable → `RunPython` backfill → `RemoveConstraint`/`RemoveField` → `AlterField`, dentro da MESMA `Migration`, nunca uma migration que apaga dado antes de o novo campo estar populado.
- **CORREÇÃO (15/09/2026) — queryset de `ModelChoiceField` escopado em `__init__`, nunca como default estático de classe, é o padrão real de segurança de backend** para "campo cujas opções dependem de outro objeto já salvo" (aqui, `delivery_location` depende de `opportunity.client`) — o próprio Django rejeita qualquer PK fora do queryset como "not a valid choice" antes de `clean()` rodar, então um POST manual manipulado nunca passa. Mesmo padrão já usado por `MovementForm`/`current_location` em `apps/operations/forms.py`; reaproveitado aqui pela primeira vez dentro de `apps.crm`. Vale como referência para qualquer campo futuro do tipo "picker escopado a um relacionamento" (ex.: um futuro vínculo Proposta↔Equipamento por patrimônio).
- **CORREÇÃO (15/09/2026) — atributo HTML5 `form="id-do-form"` como alternativa a aninhar `<form>`s**: quando um bloco de campos precisa fisicamente ficar fora do `<form>` principal na árvore HTML (aqui, porque um outro `<form>` — "Adicionar produto/serviço" — fica no meio do caminho, e `<form>` dentro de `<form>` é inválido), a solução nativa é aplicar `form="<id>"` em cada campo/botão remoto em vez de JavaScript customizado para juntar os valores no submit. Descobriu, de quebra, um bug real de dois `<form>`s HTML desconexos herdado desde a RODADA 3 (campos de "Período/Logística" nunca chegavam ao backend ao clicar "Salvar rascunho") — invisível aos testes `self.client.post()` porque eles não passam pela renderização/estrutura real do HTML; só um teste de navegador real (Playwright) pegou.
- **CORREÇÃO (15/09/2026) — botão do bloco "Documento" NÃO mudou de texto**: o pedido desta rodada era só sobre a reordenação de blocos (Ajustes financeiros/Resumo financeiro/Informações complementares) — uma leitura inicial havia trocado por engano o rótulo para um texto fixo genérico; revertido a pedido do usuário. O rótulo continua dinâmico por tipo de documento (RODADA 3: "Gerar orçamento"/"Gerar contrato"/"Gerar proposta + contrato", nunca genérico), e continua nunca registrando aceite/ganho (só "Orçamento aceito", no topo da página, faz isso).
